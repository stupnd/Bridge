System Diagram

Figure X shows the end-to-end architecture. Each glove samples five flex sensors and an ICM-20948 9-axis IMU every 20 ms on an Arduino Nano ESP32 and sends the readings as a 56-byte Bluetooth Low Energy (BLE) packet. Two receivers use this stream. The Raspberry Pi body unit (blue path) receives packets from the gloves, will classify the sign being performed, and speaks the result through a USB speaker using offline Piper text-to-speech. The web application (orange path) connects to the glove directly through Web Bluetooth to display translations, guide calibration, teach signs and collect labelled training data. The web application is hosted on Vercel and uses Supabase for user accounts and the team’s shared recording dataset. Dashed boxes mark components that are planned but not yet built.

5.2 Front-End (Graphical User Interface)

The front-end is a React and TypeScript web application built with Vite and Tailwind CSS. It connects to the glove, translates signs into text, guides sensor calibration, teaches signs with live feedback, and collects labelled training data for the recognition model. It is deployed at a public HTTPS address (Section 5.4), which Web Bluetooth requires.

Since the CEG 4912 final report, the interface has been reorganized around what the user is doing rather than around the hardware: Translate, Learn, Glove, Collect, Lab and Account, plus the Login screen. Navigation uses client-side routing, and every page except Login requires the user to be signed in.

5.2.1 Glove Connection and Application Structure

In the first prototype, each page managed its own Bluetooth connection, so moving between pages dropped the connection and the user had to pair again. The connection logic was moved into a single shared component (SensorContext) that wraps every page. It opens one Web Bluetooth link to the ESP32, decodes each packet (nine IMU values as 32-bit floats followed by five flex readings as 32-bit integers) and makes the latest reading available everywhere. The glove sends about 50 packets per second, so the interface redraws at most once per screen refresh, while components that need every packet (such as the recorder) subscribe to the raw stream.

The browser connects to the glove directly; the Raspberry Pi is a second, independent receiver. This allowed the interface to be developed against the real glove while the Pi was being set up. A development-only glove simulator generates realistic flex and IMU data at 50 Hz through the same path, so team members can work without the hardware.

Calibration is shared by every page. The user holds an open hand and then a fist; the averaged readings map each finger to 0% (straight) – 100% (bent). This adapts to different hand sizes and glove fit, works whichever way a sensor’s reading changes when bent, and is saved in the browser so it survives a page reload.

User accounts use Supabase Authentication (email and password). A protected-route wrapper checks for a valid session before any application page loads.

5.2.2 Translate

Translate replaces the earlier Dashboard as the main screen. The current sign is shown in large text; holding a sign steady for 0.7 seconds types it into a running text box with Space, Delete and Clear controls, and a Pause button stops detection. When the two most likely signs are too similar to call, the screen shows both (for example “Not sure: E or S?”) instead of typing a likely wrong answer. Recognition is described in Section 5.3.

5.2.3 Learn

Learn teaches the ASL alphabet in three modes. Alphabet shows every handshape with a diagram, plain-language instructions and common mistakes. Practice with glove compares the user’s live hand with the target and gives per-finger hints such as “Bend your index more”, highlighting the fingers that are off. Quiz shows a handshape and asks which letter it is. Progress is tracked per letter and summarized on the Account page.

5.2.4 Glove (Sensor and Calibration)

The Glove page replaces the earlier Sensor and Hand Visualizer pages. It shows a live hand diagram whose fingers bend with the user’s, per-finger bend bars, the guided calibration, and the health of the motion sensor (which way the hand faces, roll and pitch, and raw accelerometer, gyroscope and magnetometer values). If the IMU stops responding, for example because of a loose wire, the page says so and the glove keeps sending flex data.

5.2.5 Data Collection (Collect)

Training the recognition model requires labelled glove recordings from several team members. The Collect page went through two versions this term.

The first version (September 2026) averaged a short burst of readings for each sign into a single row. Averaging works for static letters but removes the motion that defines moving signs such as J, Z and HELLO: the average of the start and end of a movement is an in-between hand shape that never actually occurs. When the team decided on one sequence-based model for all signs, the page was rewritten (October 2026) to keep every frame:

  • Sessions: a participant ID and left or right hand, then a guided open-hand / closed-fist calibration stored with the session so recordings can be re-normalized later.
  • Sign types: Static (1.5 s), Moving (2.5 s) and None (2.0 s, a resting hand). Labels are free text, so whole signs such as HELLO can be recorded, and the window can be changed.
  • Frame-by-frame capture: after a countdown, every packet in the window is stored with its timestamp, five raw and calibrated flex values and nine IMU values. Each sample is flagged if its rate drops below 15 Hz or the IMU is not reporting.
  • Storage: recordings autosave in the browser and export as a frame CSV plus a calibration CSV.
  • Team dataset: each recording also uploads to a shared Supabase database as one row with its frames stored as JSON (about 125 frames for a 2.5-second sign), which avoids the row-per-frame volume that made the first version’s syncing impractical. Only team members can read or upload (Section 5.4).

5.2.6 Lab

The Lab is a workbench for testing and improving recognition. A virtual glove (one slider per finger) lets the team try any hand shape without hardware, load a recorded letter and add random “wiggle” to see when it breaks; a live glove mode does the same with the real glove. For each hand shape it shows the predicted sign, the five closest signs and how far each is. Training samples can be added from the current hand, imported from CSV, from the Collect page or from the team dataset, and exported. Teach it your hand walks a new user through every static letter (plus a resting hand) for one to three rounds so the model adapts to them. A robustness test reports, for each letter, how often it is still recognized under noise, how often the system says “unsure”, and how often it gives a wrong letter.

5.3 Sign Recognition

Rule-based baseline (until October 2026). Each letter was described as a pattern of bent and straight fingers. This needed no training data, but it could only recognize 10 of the 26 letters (A, B, D, F, I, L, S, U, W, Y). The rest share their finger bends with another letter: E, M, N, S and T are all closed fists that differ by thumb position; U, V, R and H differ by finger spread or crossing; G/L/Q and K/P differ by orientation; and J and Z need movement. This showed that flex sensors alone cannot separate every sign, which is the main reason for the IMU and a trained model.

Current: data-driven nearest-neighbour model. The hand-written rules were replaced by a model learned from recorded samples. Each sample is five calibrated bend values; a live hand is labelled with the sign of its closest sample, measured as the average difference per finger. Adding or replacing samples retrains it instantly. It recognizes all 24 static letters. Three safeguards make it usable live:

SafeguardSettingPurpose
RejectionNo sign if the closest sample is more than 25% awayA relaxed hand or a transition between signs types nothing
Confidence gate“Unsure” if the best match is less than 15% closer than the secondShow “E or S?” instead of a likely wrong letter
SmoothingA sign must win 60% of the last 0.3 sStops flicker from sensor noise

Why nearest-neighbour now, and why a different model later. With only one recorded sample per letter, a trained classifier would simply memorize those samples, so nearest-neighbour gives the same result while staying transparent (the Lab shows exactly which samples a decision came from) and needing no training step. It is an interim baseline for static handshapes. It cannot recognize signs defined by movement, because it compares a single hand shape. Once multi-person data has been collected, the team will train the planned sequence-based model, which reads the whole recording over time, uses the IMU, and covers letters and word signs together. It will be compared against this baseline using leave-one-person-out evaluation (train on everyone except one person, test on that person).

A second experimental tool, Motion Lab on the Collect page, already compares a k-nearest-neighbours classifier on flex-only features with one on flex plus 9-axis features (hand orientation, rotation, jerkiness and back-and-forth motion), and tests simple motion rules for J and Z. It has not yet been evaluated on real data.

5.4 Cloud Services and Deployment

The system has no custom backend server. The web application runs in the browser and uses two hosted services.

Supabase provides email/password accounts and a Postgres database for the team’s recordings. The prototype tables from last term were replaced on October 23; one of them had access control disabled, so anyone holding the public key could read or edit it. The new design has three tables (team_members, recording_sessions and recordings) protected by row-level security: signed-out visitors have no access, only accounts on the team list can read or upload, users can change only their own recordings, and no one can add themselves to the team from the application. These rules were verified with eight tests that impersonate a team member, a signed-in outsider and a signed-out visitor; all eight passed. Database changes are kept as version-controlled migration files in the repository.

Vercel hosts the web application over HTTPS, which Web Bluetooth requires. It is connected to the GitHub repository: changes merged into the main branch deploy to the public site automatically, and every branch or pull request gets its own preview link. A GitHub Actions check type-checks and builds the application on every pull request. Unused code and packages from the original Figma prototype were removed (runtime dependencies went from 49 to 9).

Li-ion Battery Safety (draft for the hardware team)

  • Use only packs with built-in protection (over-charge, over-discharge and short-circuit) and charge them with a matching charger.
  • Never charge unattended or while worn; charge on a non-flammable surface or in a LiPo-safe bag.
  • Insulate all exposed terminals and connectors; add a power switch and an inline fuse between the pack and the circuit.
  • Inspect packs before each use; stop using any pack that is swollen, punctured, hot or damaged.
  • Keep packs away from sweat and moisture inside the glove and body unit, and allow for airflow.
  • Store at partial charge and dispose of damaged cells through proper battery recycling.
